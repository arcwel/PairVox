# Threat model

PairVox lets you steer an agent that can edit files and run commands, by voice. Speech recognition makes mistakes, and other people or devices can make sound near your Mac. This document covers what can go wrong and what PairVox does about it.

## Assets

- Your source code and machine: the agent can edit files and run shell commands.
- Your Claude account or API key.
- Audio from your room.

## Trust boundaries

1. **Microphone → transcript.** Untrusted: misrecognition, background speech, TV or video audio, other people.
2. **Transcript → Claude Code.** Treated as your instruction, the same as typing it.
3. **Claude Code → tool execution.** Gated by Claude Code's own permission system and, when it asks, by PairVox's policy.
4. **Tool output and web content → Claude → speech.** Untrusted: prompt injection can make Claude say or request anything.
5. **The opened repository → the Claude child.** Untrusted: a downloaded repository can ship `.claude/settings*.json` (hooks, allow rules), `.mcp.json` and `CLAUDE.md`. PairVox starts the child with `--setting-sources user` unless you turn on “Load this project's own Claude Code settings”.

## Controls

| Risk | Control |
|---|---|
| A misheard “yes” approves something destructive | `PermissionPolicy` rates every request. What is read aloud is a one-line summary (the file name and whether it is in the project, or a command's first step and how many more it has). The whole command is on the card. With the default setting “Approve by voice from the summary” a spoken yes answers that line for an ordinary multi-step command, so the owner accepts that the rest was reviewed on screen, if at all. Off, a command too long to read in full needs a click. Whatever the setting, the summary never stands for what it cannot describe: a command with redirection into a file, command substitution, backticks, a heredoc or process substitution, or one whose readout collapses to “a command”, is screen-only (joining stderr to stdout, `2>&1`, is not a redirection). So is anything that reaches the network, and that includes fetching code to install or run: `npm install`, `pip install`, `go get`, `brew install`, `npx`, `bunx`, `uvx`, `pnpm dlx`, `open <url>` and the rest, found by program name after quote removal, so `cu''rl` is curl. The same list keeps a command out of a folder shell grant. Turning the setting off reaches every open project at once and re-rates the request on screen. A spoken yes, the high-risk phrase and “allow all” stop counting for a request that has waited more than five minutes (the age limit the announcer and the phone link share). The card still works. From another project's announcement, “approve” is offered only for a request its one line fully describes, the same test the menu bar applies. A long command is switched to or answered on its card. A shell command is “low” only when it is a plain read-only command (`ls`, `git status`, `grep`, …). Anything it does not recognize is at least “review”, and git global options such as `-C` are stripped before matching. Refusals (“don’t always allow”, “never ask again”) are parsed before approvals. High-risk requests can never be approved by voice: a spoken yes gets “please confirm on screen”. High risk covers recursive or forced `rm`, `git push`, `reset --hard`, `sudo`, piping a download into a shell, publishing, `launchctl`, writes outside the project, credentials and dotfiles, and anything Claude Code itself flags (`safetyCheck`, `default_to_no`, `requires_user_interaction`). |
| Background speech triggers actions | VAD needs about 180 ms of sustained speech above an adaptive noise floor. Yes/no answers are only recognized while a prompt is pending and only as short whole utterances; longer speech becomes feedback to Claude, never an approval. A question ("Is that okay?") is never an answer, and a spoken answer counts only if it was begun after the request's prompt started playing, so a reply to Claude's previous sentence cannot approve a request nobody has heard (audit run 6). Push-to-talk and mute are one keystroke away. |
| TTS echo heard as user speech | Voice-processing I/O (Apple's echo canceller) plus a VAD threshold raised by 6 dB during playback, kept for 0.5 s after playback ends. A spoken approval made of the last prompt's own words, begun while it played or within 0.6 s after, is not counted; "yes" is never in a prompt. The phone, which has no echo canceller, applies the same rule to what it last said (audit run 7). Barge-in can be turned off (half-duplex). If the user turns on spoken confirmation of high-risk requests, PairVox's own prompt contains the phrase that approves them, so speech the microphone hears can approve a high-risk request; the setting is off by default and says so. |
| An MCP tool sends, posts or deletes something outside the Mac | The card lists the arguments the tool will be sent, and an MCP tool (`mcp__*`) is approved on screen only, never by voice. Repository MCP servers are not loaded unless the owner trusts the project configuration (`--setting-sources user`). Printing the environment (`printenv`, `env`, `export -p`, any mention of `ANTHROPIC_API_KEY`) is high risk and never covered by a folder grant (audit run 6). |
| Prompt injection asks for dangerous actions | The same permission gate applies whatever Claude says. Spoken prompts describe what will actually run, taken from the tool input and not from Claude's own `description` field. The on-screen card shows the whole command in a scrollable box. Requests are shown and spoken one at a time: a second request waits in a queue and never replaces the one on screen, and every button is bound to the request ID it was drawn for. “Always allow” applies Claude's suggestions to the session only. |
| Credential exposure | No login UI. `scripts/check-keychain-access.sh` reports which programs the Keychain lets read the saved key without a prompt. Subscription credentials never pass through PairVox. An API key is stored only in the Keychain (`kSecAttrAccessibleWhenUnlocked`), passed only to the child process environment, never written to settings or logs. The child's environment is the login shell's minus a deny-list (`ChildEnvironment`, applied to the session, the advisor call and `claude --version`): every `ANTHROPIC_*` variable (so a forgotten `ANTHROPIC_BASE_URL` or `ANTHROPIC_CUSTOM_HEADERS` in `.zshrc` cannot send the key elsewhere, and a shell key or token cannot override the chosen auth mode; in API-key mode `ANTHROPIC_API_KEY` is then set from the Keychain and is the only `ANTHROPIC_*` variable the child sees), every `CLAUDE_CODE_*` variable and `CLAUDECODE` (`CLAUDE_CODE_OAUTH_TOKEN` is never forwarded in either mode; the Bedrock and Vertex switches and nested-session markers go with it), `CLAUDE_CONFIG_DIR` (another settings folder would mean other hooks, servers and credentials), and the Node and TLS variables that load code into the child or let a proxy read its traffic (`NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_USE_SYSTEM_CA`, `SSL_CERT_FILE`, `SSL_CERT_DIR`). Proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`) pass through on purpose: a user behind a proxy has no other way to reach the API, and with the TLS variables dropped a proxy sees the tunnel to `api.anthropic.com`, not the key. The captured environment is held in a private field of the app model, never in a published value. `pairvox-cli --env-audit` (`--json` for scripts) shows what the filter does to this Mac's login shell: the dropped names with their reason group, the proxies that pass and whether each is set, and the count forwarded, never a dropped value. |
| Leaking audio or transcripts | Speech recognition and synthesis run on-device. No telemetry. The only network traffic PairVox itself makes is model downloads, which for the Kokoro files are pinned by SHA-256 and loaded only after verification. The Whisper speech models and their tokenizers are downloaded by PairVox from Hugging Face at pinned commits and checked against pinned SHA-256 hashes before WhisperKit loads them (`scripts/pin-whisper-models.py` regenerates the pins). |
| Malicious model file | Kokoro's loader traps on malformed input, so files are hash-verified before loading. Whisper models are hash-pinned the same way (see above), and a file that does not match is deleted and refused. |
| A hung CLI blocks the app | Unsupported control requests are answered with an error immediately. Process exit is detected and reported; the next message resumes the session. |

| An AI explanation of a request misleads the approver | It is advice shown beside the real command and labeled as an AI summary, comes from a separate read-only call that cannot approve anything, treats the request as fenced data, and is never what is spoken as the approval prompt. |

## Not in scope / known limitations

- PairVox does not sandbox Claude Code. Use Claude Code's own settings (permission rules, sandboxing) for defence in depth.
- “Auto-approve read-only tools” is off by default and answers only plain read-only tools (never shell commands, never `ExitPlanMode`, never a file that looks sensitive). Reading files can still pull sensitive content into the conversation.
- Hands-free mode in a shared space is inherently riskier. Prefer push-to-talk there.
- The risk classifier is heuristic. Since audit run 2 it reads the program and subcommand as well as the text (long flags, `git -p push`, `/usr/bin/sudo`, pipe into an interpreter), but shell grammar is open-ended: it errs toward asking, and a folder shell grant refuses braces, backslashes, quote tricks, `cd` without a target and anything it cannot place. It is still not a security boundary on its own. See `docs/security/2026-10-13-audit-run-2.md`.

## Phone link (v0.3, off by default)

The Mac listens only when you switch it on, accepts connections only from Tailscale (and loopback) addresses, and lets a peer in only after a keyed handshake with a key created when you clicked Pair. Frames are encrypted and numbered; replays end the connection. The Mac, not the phone, decides what a spoken yes may approve. Phone keys on the Mac live in the Keychain (not in the phone list file) unless the build is positively a local development build (ad-hoc, or an Apple Development certificate); those keep them in a separate private file (0600) because the Keychain would ask again after every rebuild (see `docs/DEV_ENVIRONMENT.md`; in those builds a same-user process can read the keys and can plant a phone without the Pair click). A signature PairVox cannot place, such as an App Store or TestFlight re-signature or a failed Security call, gets the Keychain, and `PAIRVOX_KEYSTORE=file` is ignored outside development builds, and a phone file carrying a key is trusted only once, on the first run. Before the handshake, the Mac tells a phone it will not talk to why (not paired, removed, or a different protocol version) so the phone stops retrying; device IDs are random 128-bit values, so this says nothing to a peer that does not already hold a phone's ID, and the pre-authentication rate limits still apply. A wrong key is not distinguished from a dropped connection. A refusal is not authenticated, because it is sent before any key is tried: anyone who can answer at the Mac's address could make a phone stop retrying and show its pair-again prompt, but nothing such a peer says can pair a phone, approve a request or read anything, and the phone tries once more each time the app comes to the front. The `pairvox-link` tool talks to the app over a private socket (0600, same-user only); it can start a pairing offer but pairing still needs your click. Pairing uses only a one-time 16-byte random secret, shown as a QR code and as a link you can copy. It expires after two minutes and works once. There used to be a six-digit code as well: its secret was the six digits, so anyone who captured one pairing exchange (on the loopback leg of a userspace Tailscale forward, or on an endpoint) could try all million codes offline, open the grant and hold that phone's long-term key. It was removed on 2026-10-17. A copied link sits on the clipboard, where other apps on the Mac (and the phone, through Universal Clipboard) can read it while it is valid. It still needs your Pair click, and the Pair dialog names the phone. Known gaps: the link has not been fuzzed or independently audited.


Runs 3 and 4 of the audit cover the phone link, the iPhone app, cross-project approvals and the control channel: see `docs/security/2026-10-13-audit-run-3-phone-link.md` and `2026-10-13-audit-run-4-cross-project.md`.
